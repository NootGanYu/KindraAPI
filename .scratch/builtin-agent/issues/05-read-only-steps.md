**What to build:** 一个批准的计划连续读取多个接口并汇总，显示各步骤状态。

**Status:** resolved

父规格：[内置 Agent 规格](../spec.md)。22 张票共同构成已确认首版；新增工具复用两协议的协议无关工具契约。

验证约定：使用 Renderer 实际调用的应用命令/事件、隔离 userData、真实存储及业务能力；按需使用回环模型和目标 HTTP，关键用户旅程覆盖 Electron UI。

- [x] 范围内连续步骤不重复确认；扩展对象或范围暂停重新授权。
- [x] 显式依赖失败时暂停依赖，已证明独立步骤可继续；未知依赖保守阻塞。
- [x] 计划、工具结果及会话均本地持久化、重启可读、不进入 Git，保留至用户手动删除。
- [x] 应用命令集成测试验证部分失败、顺序及计划状态。

## Answer

已将 04 号票的只读计划扩展为多个接口和步骤组成的任务图，保持单接口命令兼容。模型在一次响应中提出完整读取步骤及依赖；用户一次批准后，主进程逐步复核范围并按依赖顺序读取，统一发送脱敏工具结果供模型汇总。

- `ReadPlanInput.targetIds/drafts` 支持多个对象及各自未保存草稿；所选连接、项目、环境与草稿快照固定于计划生成时。
- `read_api` 可声明 `step_id/depends_on`。显式空依赖表示独立；省略依赖时保守依赖此前步骤，缺失引用和循环依赖暂停。实际读取失败标记 `failed`，该对象后续步骤及依赖暂停，明确独立步骤继续。成功结果保留，重复批准拒绝执行。
- 模型扩展项目、对象、工具或参数范围时暂停并要求新计划授权；工具结果中的指令不会增加权限。
- 面板支持多选、逐步骤对象/来源/依赖/状态/错误显示，保留部分成功及汇总。计划、脱敏结果与历史继续使用本机存储，可重启查看及手动删除；重启不自动读取或重放。既有项目会话存储行为保持不变。

TDD 验证：先观察多工具计划被拒绝、失败后所有步骤均暂停、界面不能选择多个接口的失败，再分别实现批量计划、依赖调度和 UI。

通过 `typecheck`、`build`、`test:agent-plan-steps`、`test:agent-plan-steps-ui`、`test:agent-plan`、`test:agent-plan-ui`。命令测试覆盖单次批准、草稿、顺序、乱序依赖图、部分失败、明确独立、未知/循环依赖、越权与防重放；真实 Electron 验证部分成功、重启和删除。04 的 Git 边界与单对象旅程回归通过。

用户提供的真实服务中，`glm-5.3` / Chat Completions 完成双接口计划、一次批准及汇总；仅使用隔离 userData，不输出或提交密钥。
