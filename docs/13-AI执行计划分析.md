# 13 · AI 执行计划分析

调研日期：2026-11-03。Kindra 代码基线：`7524381`；原版：本机 Apipost 单机版 2.0.0。原版四个相关 chunk 与安装包逐字节比对，范围限所检查执行计划和 MCP 相关代码，不代表整个应用。

## 结论与范围

原版单机版的执行计划允许用户独立编排，也允许 AI 经 MCP 参与编排、执行和分析。**内置 Agent 不是执行计划的前置条件。** 用户在本轮后续确认：利用外部 MCP 即可开始建设 AI 执行计划，不再等待另一个任务的内置 Agent 底座；当前已进入可编码规格阶段，见 [执行计划规格](../.scratch/ai-execution-plan/spec.md)。用户已选择主动暂停、编辑并保存接口后，让后续步骤使用新保存版本；暂停发生在当前逻辑步骤完整结束后，保存变更并预览受影响步骤后由用户手动继续。

本分析分别标注原版界面观察、官方帮助说明和 Kindra 静态代码证据；未实际发送 API 请求或验证原版执行结果。网页版右侧 AI Assistant 的观察属于另一产品界面，不能据此认定与单机版计划是同一模块。

## 术语对照

| 概念 | 内容 | 生命周期与边界 |
| --- | --- | --- |
| Agent Plan | Agent 为完成用户目标提出的多步任务计划，可包含读取、修改、执行、保存等动作 | 服务于一轮授权任务；授权和依赖不等于接口流程定义 |
| 原版 MCP Execution Flow | 用户或外部 AI 编排的接口执行计划，含步骤快照、覆盖输入及步骤脚本 | 可保存、修改、重复执行，由 MCP 提供外部访问 |
| Kindra Flow | `Flow` 事件树，包含 API、请求、脚本、断言、条件、等待、分组和循环 | 可由页面或 MCP 工具创建，但两者表达能力不同 |
| Run | 一次 Flow 执行的结果和报告 | 记录执行状态和结果，不等于计划定义或 Agent Plan |

原版的“AI”名称和 `source=mcp` 标记表明外部 AI 可规划、调用工具并接收结果；已追踪的本地链路不包含模型调用。不能据此推断模型框架。

## 原版可观察行为

在本机 Apipost 单机版点击顶部“AI执行计划”，打开独立执行页面。页面说明：“可由用户或 AI 独立或共同编排，自动执行并生成报告，再通过 MCP 同步给 AI 诊断代码。”旁边提示“AI需开启 MCP 连接，打开教程”。页面有“执行计划”“执行记录”两个页签，空态提供“新建计划”。这是界面观察，并非对执行行为的动态验证。

[Apipost 单机版官方帮助：AI 执行计划](https://offline.apipost.net/help/executions/) 说明：

- AI 连接需要开启 MCP 服务并授权项目；AI 创建、修改或执行计划还需要项目写入权限。计划可供用户检查和修改。
- 计划仅支持当前项目的 HTTP 接口；同一接口可重复加入，每步独立配置参数、认证、Cookie 和前后置脚本。
- 保存的是接口快照，之后修改 APIs 不会自动改写已保存计划；运行计划步骤所配置的脚本，不执行接口页面原有的内置脚本。
- 步骤按顺序串行执行，即使一步失败也继续其余步骤；请求出错、HTTP 状态非 200 或断言失败均标记失败，预期 4xx 也会被记录为失败。
- 执行记录包含逐步结果，最近保留 50 条；记录可交给 AI 继续分析。

这些是厂商文档所述语义，不能推断其内部模型、框架或 Agent 实现，也不代表 Kindra 必须照搬所有规则。

### 执行链与数据

```mermaid
flowchart LR
  A[用户或外部 AI 编排] --> B[计划与步骤快照]
  B --> C[串行执行]
  C --> D[本地运行记录]
  D --> E[MCP 返回摘要或读取报告]
```

在所检查实现中，步骤的 `target_id` 标识接口，`api_snapshot` 保存接口快照，`mcp_input` 记录 MCP 改动标记及差异；`pre_script` / `post_script` 是步骤脚本。更新时保留旧快照，不允许直接更换已有步骤的目标；需要变更目标时删除后重新添加。JSON body 的差异仅保存与快照不同的 key，删除项记录在 `mcp_deleted_body_keys`；执行时以 `input.body` 整体替换 body。它们描述执行流程数据，而非 Agent 的自然语言任务计划。

### 本机安装包静态证据

本机单机版 2.0.0 的执行计划相关代码经解包静态分析，四个相关 chunk 已与安装包逐字节比对。此证据适用于所检查版本，不等同于运行时执行验证：

- MCP 创建及更新工具返回可以直接执行，执行路径没有观察到计划审批关卡；界面运行按钮受运行锁约束。`source=mcp` 的计划在 UI 标为 AI，已追踪链路本身没有发现模型请求。
- 新增步骤时保存接口快照，旧步骤保留快照并禁止更换目标；执行使用快照，清除接口自身的前后置脚本后追加步骤脚本。普通失败继续，最后汇总；非 200 标记失败，最多保留 50 条记录。
- 已追踪链路为 stdio → 本地 TCP → mcpService token → Renderer IPC → 保存 flows → 运行 → 保存 runs → 返回摘要或读取报告。
- **官方说明与本机代码的权限行为不同：**官方帮助要求 AI 创建、修改或执行计划开启项目写入权限；所检查本机代码中创建、更新检查执行权限，删除检查写入权限。差异原因未确定，应并列看待，不推断其他版本行为。

## Kindra 当前实现

- [顶部入口](../src/renderer/src/components/TopBar.tsx) 指向 `/automation`；[自动化页面](../src/renderer/src/pages/AutomationPage.tsx) 管理局部 Flow 草稿，运行时先无条件保存再执行。主进程 [IPC](../src/main/ipc.ts) 从磁盘读取 Flow。因此现有页面不是未保存草稿的独立执行路径。
- [Flow 类型](../src/shared/types.ts) 是包含八种节点的事件树；[MCP 工具](../src/main/mcp/tools.ts) 将步骤转为 script-api-script 事件，不支持通过该步骤接口表达条件或循环，更新时重建事件 ID。create、update、get、execute 工具分别位于该文件约 981、1016、1064、1094 行。
- MCP 工具权限依赖 MCP 配置，调用来源固定为 `mcp`；`execute_api` 标记为无需写权限，但 `save_response` 路径可写接口定义。共享业务能力时需要单独明确内置 Agent 的身份及权限，不能简单套用该配置。
- [执行引擎](../src/main/flow/engine.ts) 每步实时读取 Target；请求使用 `flow.env_id`，运行时使用调用方传入的 `environmentId`，存在环境不一致风险。步骤失败后继续。`runFlow` 当前没有贯穿的取消信号或进度接口，运行结束后保存报告。
- [存储实现](../src/main/storage/store.ts) 将定义放在 `executions/flows`，报告放在 `executions/runs`。[Git 初始化](../src/main/git/git.ts) 仅在初始化新仓库且尚无 `.gitignore` 时写入 `executions/runs/` 忽略规则；既有仓库或已有 `.gitignore` 不会补写。报告是否进入 Git 取决于仓库状态和规则。
- [退出处理](../src/renderer/src/App.tsx) 会自动保存 dirty API，[项目切换](../src/renderer/src/store.ts) 会清除草稿。这与既有 Agent 草稿和退出暂存策略需要协调。

例如 Flow 保存环境 A、调用方传入环境 B 时，运行时变量选择 B，而请求仍传 A，可能导致脚本使用的变量与请求环境不同。环境应在一次运行入口统一绑定。

原版执行快照会清除接口原脚本，仅执行步骤脚本；Kindra 则实时读取 Target 并经请求执行路径处理，不能假定具备同样的脚本隔离语义。Kindra 的事件树可表达条件和循环，但 MCP `steps` 适配只生成脚本、API、脚本序列，不能完整往返这些节点。现有失败继续语义也不能满足 Agent 按依赖暂停：如登录失败后使用其 token 的步骤应暂停，能证明独立的步骤可以继续。取消需贯穿运行及请求链，已发出的远端请求不能视作自动撤销。

上述为静态代码分析，行为应在实现时重新核对。

## 工作安排与底座交接

**最新安排（2026-11-03）：**用户确认以外部 MCP 编排为入口，执行计划可独立进入编码，不再以内置 Agent 完成为前置条件。这替代此前“先分析、等待 Agent 底座”的排期。另一个任务继续负责内置 Agent；本功能复用现有执行能力并提供独立运行控制，避免把聊天、模型供应商或会话系统带入本期。已发布的 [规格](../.scratch/ai-execution-plan/spec.md) 是后续实现依据；下列为将来对接内置 Agent 的边界建议。

建议约定以下交接契约：

- **项目身份与授权：**每轮绑定项目、调用身份和允许的读取、修改、执行范围；外部 MCP 和内置 Agent 各自执行策略，不互相借用权限。
- **草稿快照与版本候选：**明确读取哪个草稿、候选和正式版本，传递版本标识及冲突信息；已批准计划明确包含 save 步骤时，校验通过后自动保存正式定义，无需重复授权。
- **取消与工具事件：**传递任务、步骤、进度、取消和结果事件；取消不能声称撤销已发送的远端请求。
- **运行结果引用：**Agent Plan 可引用 Flow 和 Run 的稳定标识、版本及结果；Agent 的任务计划、可重复运行的 Flow 定义、一次 Run 报告分别保存和解释。

## 运行中修改：方案比较

用户已选择的产品方向是：**主动暂停运行，编辑并保存后续接口，随后让后续步骤使用新保存的接口版本。**这在技术上可行；调研基线尚无暂停和续跑能力，这些能力已纳入本期实现规格。

| 策略 | 优点 | 代价与风险 |
| --- | --- | --- |
| 全程使用启动快照 | 本轮请求依据稳定、可追溯 | 修改只能用于下轮 |
| 每步读取最新定义 | 修改立即对后续步骤可见 | 可能混用版本，授权、依赖和追溯更难核对 |
| 快照加显式暂停及重规划 | 默认稳定，用户可检查并更新剩余步骤 | 需要暂停控制、变更预览、依赖校验和版本记录；这是已选产品方向的建议实现 |

建议默认以启动快照运行；暂停后编辑并主动保存接口，再为剩余步骤构建新快照。同一接口在剩余步骤中多次出现时，受影响的各次引用均可更新；已完成步骤保留旧版本，运行上下文中的 token、对象 ID 等继续保留，但须确认它们仍满足新步骤前置条件。报告记录切换点、已完成与剩余步骤使用的版本；变更扩大原批准范围时重新确认授权。用户请求暂停后显示“正在暂停”，当前逻辑步骤完整结束后进入暂停；保存后展示受影响的剩余步骤，由用户手动继续。运行中的版本和编辑版本应在界面区分。

建议状态模型为 `running → pause_requested → paused → reviewing_changes → running`；完成、取消、失败和远端结果未知分别表达。失败或结果未知不自动重发，已完成远端写入不自动重放。原版在创建步骤时冻结 API 快照；这里讨论的每次 Run 启动快照及暂停后剩余步骤的新快照是不同的设计决定。持久化 Flow 是否继续固定旧 API，还是在启动时读取最新定义，仍是后续设计点。

建议的快照和上下文边界：

- 启动时绑定项目、环境和 Server 地址，以及 Flow、API、继承配置、模型和脚本定义的版本或内容。请求和脚本使用同一绑定环境。
- 初始变量进入本轮上下文；步骤内提取或更新的运行变量在本轮继续传递。运行期间普通编辑默认不改变本轮；已确认的“暂停、保存、手动继续”是接口定义更新的显式入口。全局变量编辑是否另设导入入口留待后续设计，不能让共享可变状态悄悄改变当前运行。
- 对文件等外部依赖，可记录摘要并在执行前核对；发现变化时停下重审。这是建议，当前尚未实现。
- 固定定义只保证请求依据可追溯，不能保证远端服务状态或返回结果一致。中途重新规划须核对已完成步骤的输出是否仍满足新剩余步骤的前置条件，不能简单续跑，也不能自动重放已完成的远端写入。

## 后续技术落点

以下是待设计方案，现有实现尚不支持暂停续跑：

- [执行引擎](../src/main/flow/engine.ts) 的 `runEvents`（747 行）及嵌套 loop（726 行）需要持有执行游标、调用栈和运行变量，恢复时从边界继续，不能重新调用 `runFlow` 从头运行。
- 暂停边界应是完整逻辑步骤，包含前置脚本、请求、后置脚本及断言；不能在前置脚本与请求之间切换版本。当前 MCP `stepEvents` 将步骤扁平化为多个事件，需要补充逻辑分组。
- 保存时的 revision 检查及 `targetSync` 事件可评估复用；恢复前仍须再次验证版本和冲突，避免并发变更被覆盖。
- `applyRequestInput`（453 行）会将 Flow input 覆盖到新 Target，body（461 行）整体替换。因此仅刷新 `target_id` 无法保证用户保存的字段实际生效。需展示实际生效请求并校验新定义与步骤覆盖之间的冲突，再允许继续。

## 后续验收示例

这些是供后续实现评估的例子，不是已接受的架构决定：

1. 启动运行后修改接口，当前运行与编辑版本提示清楚；运行行为符合最终选定的快照策略。
2. 选择环境 B 后，脚本变量与请求均使用 B；登录提取的 token 可传递给同轮后续步骤。
3. 登录失败后依赖 token 的步骤暂停；能够证明独立的步骤按约定继续。取消不会声称回滚已发送请求。
4. 禁用外部 MCP 不意外禁用内置 Agent，也不能通过内置 Agent 绕过 MCP 自身权限。

暂停交互已确认：请求暂停后显示正在暂停，当前逻辑步骤完整结束后进入暂停；保存接口更新所有受影响的剩余步骤并展示这些步骤，用户手动继续。已完成步骤及运行变量保留，仅在授权范围扩大时重新确认。底层实现仍待设计，见 [ADR-0008](adr/0008-flow-pause-and-saved-definition-refresh.md)。
