# 内置 Agent 采用连续工具循环与逐工具风险审批

Status: accepted（2026-11-05）

内置 Agent 最初采用“先规划、再按已批准槽位执行”的计划引擎。它安全、可审计，但模型在首轮看不到项目定义，只能提交一组受限步骤；真正的读取、修改和执行必须在批准后逐个槽位发生。这与用户在 Kindra 内部连续工作、边读边改边验证的期望不一致。

## Decision

新的内置 Agent 主路径改为**连续工具循环**：

- 每轮把项目目录摘要、当前活动对象与工具清单交给模型；模型可以连续调用只读、草稿、执行、保存和配置工具。
- 工具由 `core/registry.ts` 统一注册，声明全局唯一名称、JSON Schema、风险等级、只读标记、handler 与可选审批摘要。handler 直接复用 Kindra 的 store、草稿/候选、执行快照、脱敏与文档门禁，不经过外部 MCP 的权限入口。
- 每次工具调用在时间线上形成一条 Tool Activity；结果、状态、脱敏摘要与 display 通过现有会话事件推给 Renderer。
- 本地写默认只产生本机候选或草稿。高风险工具（网络执行、正式保存、删除、配置删除）按矩阵暂停审批；审批门记录参数哈希与一次性 nonce，拒绝后相同调用不得重试。
- 每轮运行拥有仅存主进程内存的状态：unknown、成功响应捕获与审批前快照。unknown 在本轮禁止重放，新用户轮才可显式重新发起。
- 配置写入记录本机加密审计；审计保存脱敏摘要与 safeStorage 加密的 before/after，支持按 before 撤销。
- 原生轮次（turn_id）把候选、工具活动、整轮撤销与配置审计关联到同一条用户消息。

## Alternatives considered

1. **继续扩展计划引擎。** 保留现有批准槽位模型，只增加更多 operation。优点是授权边界成熟；缺点是模型仍无法先读取再决定下一步，计划槽位与延迟绑定会持续膨胀，用户也无法获得连续工具时间线。
2. **完全移除 `plans.ts`。** 直接切换到工具循环。实现更简单，但会破坏既有 22 个票据、计划授权 UI、计划命令测试与用户已保存的历史计划；风险与迁移成本过高。
3. **外部 MCP 作为唯一工具入口。** 复用现有 MCP 工具与权限，但需要伪造启用状态、把内置 Agent 绑定到外部进程边界，无法共享内存中的执行快照、候选与整轮撤销。

## Consequences

- 主 UI 从计划卡切换为工具时间线；旧 `AgentPlanPanel` 与“旧计划”模式保留为 legacy 入口。`plans.ts`、`planCommands` 与相关票据/测试不删除。
- 工具结果必须脱敏并限制大小；单条工具结果与活动 display 上限 24KB，历史超过 256KB 时折叠为摘要并保留最近尾部。
- 连续循环需要更严格的守卫：空流、参数截断、连续失败、重复读取、完全相同轮次、轮数上限与取消补齐。守卫命中返回可重发提示。
- 高风险操作不再由“批准整个计划”一次性覆盖，而是逐工具审批；审批详情必须在执行前展示方法、URL、额外请求、变量写回、保存/删除范围与风险。
- 执行/保存仍复用既有快照、revision、文档门禁与未知结果语义；配置审计是新增的本机审计面，不进入项目 Git。
- legacy 计划路径与原生循环共享模型适配、草稿/候选、执行快照、脱敏和正式保存；两条路径都必须保持测试通过。
