# 02 · 整体架构与进程模型

## 1. 启动流程

`Resources/app/main.js` 的关键顺序：

1. `app.setAppUserModelId(...)`：Windows 任务栏分组。
2. `app.requestSingleInstanceLock()`：单实例锁（防止双开写坏项目数据）。
3. 注册全局异常兜底，写入 `<userData>/main-error.log`。
4. **模块加载阶段**（`main.js:81-98`）就解析并 `require` Mock 入口
   （`build/mock.asar/server.js`），早于后面的协议注册。
5. `protocol.registerSchemesAsPrivileged` 注册 `app:` / `api:` / `apt:`
   （`main.js:269`）。
6. `app.whenReady()` 后：
   - `protocol.registerFileProtocol("app", appHandler)` → 从 `work.asar` 读静态文件
   - `protocol.registerBufferProtocol("api", apiHandler)` → 受控 HTTP 转发
   - `protocol.registerStreamProtocol("apt", aptHandler)` → 请求执行主通道
   - `initElectronServer()` 建立 Unix Socket（DB / 脚本执行）
   - `ipcAppInit` / `fileDBInit` / `licenseManager.init`
   - `createWindow()` 加载 `app://localhost`
   - `initMcpService()` 启动 MCP 本机 RPC

## 2. 五类进程/线程

| 角色 | 位置 | 职责 |
|---|---|---|
| 主进程 | Electron main | 窗口、协议、IPC、文件 DB、Mock 服务、授权 |
| 渲染进程 | `work.asar` | UI 与业务状态（zustand） |
| Worker 线程 | `utils/sendWorker.js` | 执行 `runner`，避免长任务阻塞主进程 |
| Unix Socket 服务 | `utils/newElectronServer.js` | 数据库查询、外部脚本执行（java/php/python/...） |
| Mock HTTP 服务 | `mock.asar/server.js` | 端口 30999，提供 Mock 与文档分享 |

> 【事实】`runner`（流程自动化）放到 Worker；但并非“只有”它：
> `loadrunner.js` 会 `fork(loadrunnerWorker.js)`；`newElectronServer.js`
> 用 `execSync` 执行外部脚本（会阻塞主进程）；`apipost-press.js` 会起外部
> 压测进程；`mcp-stdio.js` 是独立 stdio 子进程。旧版“只有 runner 放
> Worker”的说法已修正。

## 3. 自定义协议

### 3.1 `app://localhost`

- 从 `work.asar` 读取静态文件。
- 有路径穿越防护：`resolvedPath` 必须位于 `work.asar` 内。
- 【事实】JS 文件的 ETag 不是内容 hash，而是从**文件名末 8 位 hash 段**
  截取（`utils/utils.js:109-119` 的 `getJsHash`）。

### 3.2 `api://localhost`

- 受控 HTTP 转发（`utils.makeRequest`，使用 Electron `net.request`，
  `utils/utils.js:148/257`）。
- 历史上用于规避渲染层跨域；现在主要用于少量内部转发。
- 【推断】旧实现可能用过全局 `fetch`；当前代码已是 `net.request`。

### 3.3 `apt://localhost/proxy/<method>`（核心）

渲染层把任何 `/proxy/...` URL 改写为 `apt://localhost/proxy/...`：

```js
// 渲染层 axios 拦截器（伪代码）
if (url.includes("/proxy/")) base = "apt://localhost";
```

主进程 `aptHandler` 用 URL 最后一段作为 `method`，分发到 `send.asar`：

| method | 说明 | 响应类型 |
|---|---|---|
| `http` / `fetch` | 单次 HTTP 请求 | JSON |
| `httphar` | 生成 HAR 1.2 | JSON |
| `runner` | 流程自动化 | SSE（Worker 执行） |
| `testcase_runner` | 并发/压测执行 | SSE |
| `websocket` / `websocket_send` | WebSocket | SSE |
| `socketio` | Socket.IO 连接 | SSE |
| `socketio_send` / `socketio_update_event` | Socket.IO 发送/更新 | JSON |
| `grpc_reflection` / `grpc_proto` / `grpc_request` / `grpc_request_sse` / `grpc_reflection_mock_request` / `grpc_mock_request` | gRPC | JSON / SSE |
| `tcp` | TCP 连接与发送 | JSON |
| `query` / `test_connection` | 数据库查询/测试 | JSON |
| `loadrunner` / `stop_loadrunner` / `press` | 压测 | SSE |
| `download` | 下载文件（带进度） | SSE |
| `callFunction` | 执行自定义函数（vm，3s 超时） | JSON |

统一响应包装（`utils.HttpConvertResult`）：

```json
{ "code": 0, "msg": "success", "data": { ... } }
```

错误字符串约定为 `"message@code"`，会被转换为 `{code, msg, data:""}`。

SSE 包装（`utils.EventConvertResult`）：

```
event: request
data: {...}

event: complete
data: {...}
```

## 5. 渲染层如何发请求

### 5.1 单次请求

1. 从 store 取当前项目、环境、全局变量、系统配置、cookie、自定义函数、数据库配置。
2. 组装 `option`（见 `04`）。
3. 构造 `test_events: [{ type: "api", data: <apiEntity> }]`。
4. `POST apt://localhost/proxy/v2/http`。
5. 解析 `{code, msg, data}`，把 `data` 写入响应面板。
6. 保存发送历史：
   - `projects/<pid>/lately.json`（最近使用）
   - `projects/<pid>/send_history.json`（历史列表）
   - `projects/<pid>/send_history_results/<history_id>.json`（请求/响应/断言/console）

### 5.2 流程自动化

1. 测试用例事件树 → `test_events`（规范化见 `05`）。
2. `POST apt://localhost/proxy/v2/runner`。
3. 主进程用 `wrapSend("runner")` 起 Worker，SSE 回传：
   - `request`：每个步骤的执行结果
   - `process`：进度
   - `complete`：汇总报告
   - `systemError`：系统级异常（不是 `error`）
   - `sse`：流式片段
4. 前端按事件渲染执行树。

## 6. 本地服务与端口

| 服务 | 端口/路径 | 说明 |
|---|---|---|
| Mock / 分享 | 端口 30999（占用则 +1，最多重试 10 次）；`server.listen(port)` **未绑定 host，实际监听所有网卡**，localhost 只是示例 | `/mock/:projectid*`、`/app/mock/project/:projectid*`、`/__mock/*`、`/doc/*` |
| Unix Socket | `<tmp>/socket_<uuid>.sock`（Windows 为命名管道） | 数据库查询、外部脚本执行 |
| MCP | `127.0.0.1` + **随机临时端口**；token 存 `offline-data-local/settings/mcp_config.json`，**默认全关** | 给 AI Agent 提供项目数据能力 |
| 远程日志 | `https://apipost-fe.cn-beijing.log.aliyuncs.com/...` | `report-error.js` 上报前端错误（离线仍会尝试） |

## 7. 安全机制（值得复刻的部分）

1. **导航守卫**：`will-navigate` / `setWindowOpenHandler` 只放行内置协议与自身源，外部 http(s) 交系统浏览器。
2. **打包版 URL 白名单**：`-url=` 只允许 `app/api/apt/data` 与
   `localhost`/`127.0.0.1`；设置 `APIPOST_ALLOW_REMOTE_URL=1` 可旁路
   （`main.js:182-187`）。
3. **preload 通道白名单**：只暴露显式 API，移除了通用 `sendMessage`。
4. **Mock 管理接口**：仅回环地址 + 信任 Origin；`project_id/target_id` 白名单校验防目录穿越。
5. **协议文件读取**：`app://` 规范化后校验必须位于 `work.asar`。
6. **脚本执行**：自定义函数在 `vm` 中执行，3 秒超时；外部脚本执行有 15 分钟/10MB 护栏。
7. **请求侧**：允许忽略证书错误（产品需要），但代理/客户端证书配置可控。

> 复刻时建议保留 1/3/4/5；6/7 按你的安全需求调整。

## 8. 更新与导入

- **热更新**：`utils/upgrade.js` + `extraResources/bspatch_darwin_arm64`（二进制 diff）。
- **定时导入**：`utils/autoImportTask.js`，主进程按计划推送 `autoImport` 事件给渲染层。
- **外部脚本执行**：`newElectronServer.js` 支持 java/php/python/node/bash/go/lua/ruby/rust/bat/ps1。
- **压力测试**：两条独立机制——`loadrunner.js` 通过 `fork` 起 Worker；
  `apipost-press.js` 起 `extraResources/press_darwin_arm64` 外部进程。

这些不是复刻 MVP 的必需项，但说明了它的扩展边界。

## 9. 关键结论

- **主进程是能力中心**，渲染层只是 UI；所有危险操作（文件、网络、脚本、授权）都在主进程收口。
- **请求执行是独立的一套 Node 侧运行时**，与 UI 完全解耦，可单独替换。
- **数据是纯文件**，没有数据库；这让 git 协同、备份、离线都简单。
- **协议桥 `apt://` 是核心解耦点**：UI 只认 HTTP 风格 URL，主进程负责把不同协议/长连接/流式结果统一成 JSON 或 SSE。
