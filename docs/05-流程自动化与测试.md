# 05 · 流程自动化与测试

## 1. 概述

Apipost 的「测试用例」是一棵**事件树**，执行器逐节点运行，支持：

- 顺序步骤（接口 / 脚本 / 断言 / 等待 / SQL）
- 条件分支（`if` / `multi_if` / `assert_if`）
- 循环（`loop`，5 种模式）
- 分组（`begin`）
- 数据驱动（`iterationData` / 变量 / 响应提取）

> 【事实】运行时**没有** `case` 事件处理器（见 §3.10）。旧版把“嵌套用例”
> 列为可执行能力，已移除。

它没有引入完整的 BPMN，而是一个**轻量脚本化编排器**。对你的「简单流程自动化」需求，这套模型足够且容易复刻。

```json
{

```

### 2.1 settings 字段

| 字段 | 含义 |
|---|---|
| `env_id` | 运行环境 |
| `enable_request` | 是否记录请求明细 |
| `execute_count` | 迭代次数 |
| `interval_time` | 每轮间隔（ms） |
| `ignore_error` | 忽略错误继续执行（>0） |
| `enable_sandbox` | 脚本沙箱开关 |
| `iteration_data` | 数据驱动行 |
| `iterates_data_list` / `iterates_data_id` | 多组数据集 |

> 【事实】`frequency` 与 `settings` 同级，不在 `settings` 内（见 03 §6）。

## 3. 事件类型

### 3.1 HTTP 类

```json
{
  "event_id": "1f...",
  "type": "api",              // api | sample | request | sse
  "enabled": 1,
  "name": "查询订单",
  "data": {
    "target_id": "2dd...",
    "project_id": "...",
    "parent_id": "0",
    "target_type": "api",
    "apiData": { ... }        // 非 auto_sync 时
  }
}
```

- `api`：引用项目里的接口。
- `sample`：引用接口示例（可覆盖部分请求参数）。
- `request`：内联完整请求。
- 执行时统一走 HTTP 引擎（见 04）。

### 3.2 脚本

```json
{
  "event_id": "1f...",
  "type": "script",
  "enabled": 1,
  "name": "自定义脚本",
  "data": {
    "content": "pm.environment.set('token', pm.response.json().token);"
  }
}
```

- 【事实】脚本由 `postman-sandbox` / `uvm` 执行（Postman `pm.*` 兼容 +
  `apt.*` 扩展）；只有 `callFunction` 用 Node `vm`。
- 前置/后置脚本都可；事件类型本身不区分，靠执行顺序。

### 3.3 断言（脚本式）

```json
{
  "event_id": "1f...",
  "type": "assert",
  "enabled": 1,
  "name": "脚本断言",
  "data": { "content": "pm.test('状态码 200', () => pm.response.to.have.status(200));" }
}
```

### 3.4 可视化断言

```json
{
  "event_id": "1f...",
  "type": "assert_visual",
  "enabled": 1,
  "name": "断言",
  "data": {
    "data": {
      "type": "responseJson",
      "expression": {
        "path": "$.data.id",
        "compareType": "eq",
        "compareValue": "1"
      }
    }
  }
}
```

> 【事实】`assert_visual` 的断言体在 **`event.data.data`** 里，多一层
> `data`（`analysis/pretty/842216.js:1348-1350`）。

- `data.data.type`（断言主体）：
  `responseJson | responseXml | responseText | responseHeader | responseCookie | duration(responseTime) | responseCode | responseSize | tempVars | envVars | globalVars`
- `expression.path`：
  - JSON 主体用 **JSONPath**（`$.data.items[0].id`）
  - XML 主体用 XPath
- `compareType` 枚举：

| compareType | 含义 |
|---|---|
| `eq` | 等于 |
| `uneq` | 不等于 |
| `gt / gte / lt / lte` | 数值比较 |
| `includes / unincludes` | 包含 / 不包含 |
| `null / notnull` | 为空 / 不为空 |
| `exist / notexist` | 存在 / 不存在 |
| `regularmatch` | 正则匹配（值形如 `/pattern/`） |
| `belongscollection / notbelongscollection` | 属于 / 不属于集合（逗号分隔） |

执行时被转换为 `pre_tasks` 中 `type: "assert"` 的节点，由运行时求值并产出 `assertions`。

### 3.5 等待

```json
{ "event_id": "1f...", "type": "wait", "enabled": 1, "name": "等待", "data": { "sleep": 1000 } }
```

> 【事实】运行时只读 `event.data.sleep`；`data` 为裸数字时不会生效
> （`analysis/pretty/842216.js:2942`）。默认模型也是 `{sleep:1000}`。

### 3.6 SQL

```json
{
  "event_id": "1f...",
  "type": "sql",
  "enabled": 1,
  "name": "Database",
  "data": {
    "connectionId": "db_1",
    "query": "select * from users where id = 1",
    "isConsoleOutput": 1,
    "variables": []
  }
}
```

执行时转换为 `pre_tasks` 的 `database` 节点，使用 `option.database_configs` 中的连接。

### 3.7 条件分支

```json
{
  "event_id": "1f...",
  "type": "if",
  "enabled": 1,
  "data": { "var": "{{status}}", "compare": "eq", "value": "success" },
  "children": [ ... ]
}
```

- `var` / `value` 支持 `{{变量}}`。
- `compare` 与可视化断言同一套。
- 条件为真执行 `children`。

`multi_if`：

```json
{
  "type": "multi_if",
  "data": {
    "condition": [
      { "var": "{{a}}", "compare": "eq", "value": "1", "condType": "and" },
      { "var": "{{b}}", "compare": "gt", "value": "0", "condType": "or" }
    ]
  },
  "children": [ ... ]
}
```

按顺序组合条件，`condType` 为 `and` / `or`，第一个条件作为初始值。

`assert_if`：先跑一段脚本，根据断言结果决定是否执行 children（引擎内部类型，UI 用于「断言后分支」）。

### 3.8 分组 `begin`

```json
{ "type": "begin", "children": [ ... ] }
```

无条件顺序执行 children。

### 3.9 循环 `loop`

```json
{
  "type": "loop",
  "data": {
    "loop_type": 1,
    "enable_data": 1,
    "loop_data_type": 1,
    "loop_traverse_data": { "iterationData": [ { "id": 1 }, { "id": 2 } ] },
    "sleep": 0,
    "loop_timeout": 0,
    "limit": 10,
    "loop_variable": "{{list}}",
    "loop_fixed_value": "a,b,c",
    "loop_iteration_data": "event_id",
    "loop_extract": { "var": 1, "value": "$.data.list[*]" },
    "content": "pm.test(...)",
    "loop_condition": [ ... ]
  },
  "children": [ ... ]
}
```

**数据来源 `loop_data_type`**：

| 值 | 来源 |
|---|---|
| 1 | 事件预设的 `loop_traverse_data.iterationData` |
| 2 | 从响应提取（`loop_iteration_data` + `loop_extract`） |
| 3 | 从变量取（`loop_variable`） |
| 4 | 固定值逗号分隔（`loop_fixed_value`） |

**提取源 `loop_extract.var`**：

| 值 | 来源 |
|---|---|
| 1 | `response.body`（JSONPath） |
| 2 | `response.headers` |
| 3 | `response.cookies` |
| 4 | `response.code` |
| 5 | `request.url` |
| 6 | `request.method` |
| 7 | `request.querys` |
| 8 | `request.body`（JSONPath） |
| 9 | `request.headers` |
| 10 | `request.cookies` |

**循环方式 `loop_type`**：

| 值 | 行为 |
|---|---|
| 1 | 按数据条数循环 |
| 2 | 固定次数（`limit`） |
| 3 | 条件循环（`loop_condition` 为真继续） |
| 4 | 脚本断言通过后停止（`content`） |
| 5 | 多条件匹配后停止（`loop_condition[]`） |

每次迭代把当前数据放入 `iterationData` 作用域，子节点用 `{{字段}}` 取值。

### 3.10 关于 `case`

> 【事实】`send.asar` 的运行时 handler 表**没有 `case`**
> （`analysis/pretty/842216.js:2964-3415`）。`send.js` 里只统计
> `uniqBy(test_events, "case_id")` 用于报告（`utils/send.js:1328`）。
>
> 因此：不要实现“`case` 事件在运行时嵌套执行”；旧版这段描述已删除。
> 如果 UI 仍能发出该类型，需要在渲染层或后端预展开（**未验证**），
> 复刻时建议直接用 `begin` 分组 + 复制子事件，避免依赖该类型。
>
> 渲染层里 `case_id` 的实际用途是**报告/列表关联**：`process` 事件会带
> `case_id` 回填用例列表，AI 样例还有 `ai.sample.execute_case` 命令，
> 但都没有对应的 `type:"case"` 事件处理器。

## 4. 执行算法

核心两个函数（`send.asar` 内部）：

```
executeEvent(event, option, emit, state, results)
  ├─ handler = handlers[event.type]
  ├─ 记录 iteration.startTime / startVariables
  ├─ await handler(...)
  ├─ auto_test 模式发送 process 进度
  └─ 未开启 ignore_error 时：
       ├─ 断言失败 → throw "Assertion validation failed."
       └─ HTTP 非 2xx → throw "Endpoint request failed."

iterationEvent(events, option, emit, state, results)
  ├─ 取第一个 enabled 事件
  ├─ 取 iterationDataArr 第一项作为本次 iterationData
  ├─ executeEvent
  ├─ 递归执行剩余事件
  └─ 支持 children（if/loop/begin）
```

### 4.1 迭代

- `run` 根据 `iterationCount` 复制事件列表。
- `iterationData` 会按需重复/截断到与事件数匹配。
- 每次迭代的变量快照记录在 `iteration.startVariables`，结束时对比生成 `currentVariables`。

### 4.2 错误策略

- 【事实】默认模型 `ignore_error = 1`，即**默认继续**。
- `ignore_error > 0`：记录错误继续。
- 否则：
  - 断言有 `passed === false` → 立即中断；
  - HTTP 状态不在 2xx → 立即中断。
- 系统级异常以 `{action:"systemError", message, event_id}` 推送。

## 6. 并发/压测执行（testcase_runner）

`/proxy/v2/testcase_runner` 使用 `multithread-superagent` 并发执行：

- 最大 worker 数：`min(CPU 核数, 8)`。
- 事件：
  - `status: "inProcess"`，`data: <单条结果>`
  - `status: "inProcessBar"`，`data: { completed, total }`
  - `status: "complete"`，`data: { test_scale: { case_count, data_count }, test_results, completed, duration }`
  - `status: "cancel"`
- 断言规则来自 `utils/caseTemplate.js` 的 `expert_rules`（AI 评估规则，按 `test.id` 索引）。
- 【事实】`testcase_runner` 不使用 `event:` 行，状态在 JSON 的 `status`
  字段里；与 runner 的 SSE 格式不同。

> 这部分更偏「压测/批量回归」。你的 MVP 可以先不做，或简化为固定并发 + 汇总。

### 6.1 压测模式

- `testing_mode: functional | performance`
- `load_profile: fixed | ramp-up`
- 参数：`init_vu / init_duration / ramp_duration / final_vu / final_duration / report_time`
- 主进程另有 `loadrunner.js` 与外部二进制 `press_darwin_arm64` 负责高并发压测。

## 8. 复刻建议（针对“简单流程自动化”）

### 8.1 最小可用模型

```ts
type Step =
  | { id: string; type: "http"; request: HttpRequest; saveAs?: string }
  | { id: string; type: "script"; script: string }
  | { id: string; type: "assert"; subject: string; path: string; op: string; value: any }
  | { id: string; type: "wait"; ms: number }
  | { id: string; type: "if"; cond: Condition; children: Step[] }
  | { id: string; type: "loop"; source: LoopSource; children: Step[] };
```

### 8.2 执行器伪代码

```ts
async function runSteps(steps, ctx) {
  for (const step of steps) {
    ctx.emit({ type: "step-start", id: step.id });
    switch (step.type) {
      case "http": {
        const res = await sendHttp(step.request, ctx);
        ctx.vars.last = res;
        if (step.saveAs) ctx.vars[step.saveAs] = res.json();
        ctx.emit({ type: "step-result", id: step.id, request: res.request, response: res.response });
        break;
      }
      case "script": runScript(step.script, ctx); break;
      case "assert": assert(step, ctx); break;
      case "wait": await sleep(step.ms); break;
      case "if": if (evalCond(step.cond, ctx)) await runSteps(step.children, ctx); break;
      case "loop": for (const row of resolveLoop(step, ctx)) await runSteps(step.children, { ...ctx, row }); break;
    }
    ctx.emit({ type: "step-end", id: step.id });
  }
}
```

### 8.3 变量与作用域

建议至少三层：

1. `env`（环境变量）
2. `globals`（全局变量）
3. `run`（本次运行的临时变量，脚本可写）

优先级：`run > env > globals`。支持 `{{name}}` 替换，也支持脚本 `ctx.get/set`。

### 8.4 断言与记录

- 每个 HTTP 步骤都记录完整 request/response（用于回放）。
- 断言结果单独记录 `{name, passed, expected, actual}`。
- 报告汇总：总步骤、成功、失败、平均耗时、平均响应大小。

### 8.5 不建议一开始做的

- 5 种 loop 模式（先做「按数组循环」）
- 多条件/断言分支（先做单条件 if）
- 嵌套用例引用（运行时没有 `case` handler，需自行预展开）
- 并发压测
- 定时调度
- AI 生成测试用例

这些都可以在核心链路稳定后增量补齐。

## 9. 关键坑

1. **变量替换时机**：脚本里设置的变量要能影响后续步骤的 URL/header/body。
2. **错误中断策略**：原应用默认 `ignore_error=1`（继续），但这会让报告
   包含失败步骤；复刻时建议明确默认值，并在 UI 上暴露该开关。
3. **循环中的变量隔离**：每轮迭代要有独立作用域，避免上一轮污染下一轮。
4. **长流程取消**：需要可中断信号（AbortController / worker terminate）。
5. **报告体积**：完整 request/response 可能很大，建议列表存摘要、详情按需加载。
6. **脚本安全**：如果允许任意 JS，需要 `vm` + 超时 + 禁用危险 API（或明确只给可信用户用）。

## 10. 复核补充（2026-10-24）

1. **loop**：空数据直接 0 次；`enable_data` 控制是否启用数据源；
   `loop_type=4` 会合成一段 `script` 事件；固定值循环用
   `{$key,$item}`；`loop_type=3` 接受对象、`=5` 接受数组。
2. **错误中断边界**：`sse` / `sql` 不参与“断言失败即中断”的判定；
   `systemError` 之后仍会发 `complete`。
3. **进度统计**：`process` 只统计顶层 `enabled` 事件（含非 HTTP）。
4. **SSE 事件形状**：`if / multi_if / assert_if / wait` 的 `data` 与
   `status` 与 `request` 不同，文档只给了 `request` 的完整形状；
   复刻时应为每种 action 定义独立类型。
5. **报告断言计数**：`complete.data.assert` 是步级计数；
   `success_assert` 实际是失败断言数组。
