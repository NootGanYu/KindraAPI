# 11 · Agent 集成调研

> 目标：分析 Apipost 右侧 AI 助手的可观察行为，并提出可落地的 Kindra 内置 Agent 方案。
> 调研日期：2026-11-03。本文区分实测、静态线索、官方资料和设计建议，不将后者视为 Apipost 内部实现事实。

---

## 1. 结论

Kindra 已有接口数据、执行器和 MCP 工具，适合在 Electron 主进程增加独立的 Agent 运行时，在现有界面加入右侧面板。业务能力应通过共享工具层调用，内置 Agent 与外部 MCP 分别执行权限策略。

首版确定建设支持连续操作的 Agent，默认在当前项目范围内脱敏读取，按项目保存可删除的本地会话并支持重启续聊，会话不进入 Git。用户自填 API 地址、Key 和模型名，首批使用 OpenAI 兼容接口；首版覆盖 HTTP 接口、单接口用例、请求及用例执行分析和跨接口执行流程；按本轮计划授权，允许读取和操作未保存草稿，并明确配置 Chat Completions 或 Responses。默认修改草稿并用草稿测试；保存定义须作为独立计划步骤获批。具体工具及执行快照等细节仍待确定。

Apipost 访客页面和静态调用链已观察；登录后的成功生成与服务端行为仍待验证。不能凭相似界面或公共 MCP 文档推断其模型和框架。

首版需要 Agent loop 与共享工具注册能力，支持连续操作；应保留原有 MCP 行为，并依据后续访谈确定能力范围和授权边界。

## 2. Apipost 的可观察行为

### 2.1 页面与入口（浏览器实测）

在 [Apipost 访客工作区](https://workspace.apipost.net/guest/apis) 点击右侧紫色入口后，展开 **AI Assistant** 面板，包含四个热门任务：规范化参数命名、一键补全文档、AI 生成模拟数据、批量更新参数值/补全参数描述。补全文档界面关联当前示例接口的名称和 URL。[查看展开状态截图](images/apipost-ai-assistant.png)。

选择“AI 生成模拟数据”后可输入业务场景。输入虚构商品名称的测试提示并点击生成，访客页面提示“请登录后使用该功能/游客模式”；没有得到成功的 AI 响应，也没有观察到实际业务写入。测试输入已清除。页面未发现 iframe；结合 DOM 和前端组件代码，面板表现为应用内组件。

这些观察支持它是围绕 API 操作的**任务式 AI 助手**；不能据此认定它具有任意任务规划或自主多轮工具调用能力。附件、通用聊天及实际生成后的操作未通过成功会话验证。

### 2.2 静态调用链（未动态验证）

- 字段名称和值生成调用 `/api/ai/parameters/completions`，请求数据包括 `project_id`、任务 `type`、输入、语言、任务类型以及接口名称、URL、方法等上下文；补全文档使用同一端点的 `ai_auto_complete_document` 类型，并包含接口请求、响应等字段。

- 补全文档的静态路径将生成字段应用到副本、展示进度，并提供“不采纳”“保存”“保存并分享”；保存再调用现有数据接口。实际审批和保存行为未在登录态验证。

上述相对路径属于网站自身实现线索，可能要求登录及内部上下文，不应当作面向第三方稳定开放的 API。模型名称、供应商、服务端框架、是否使用 LangChain、MCP 或自主工具循环均无法从这些证据确认。

## 3. Kindra 现状

### 3.1 界面和上下文

- [package.json](../package.json) 已包含 Electron、React、Ant Design、Zustand 和 `react-resizable-panels`；当前无 AI SDK 依赖。
- [App.tsx](../src/renderer/src/App.tsx) 的应用 Shell 可承载全局右侧面板，面板尺寸和开关可保存在界面设置中。
- [TopBar.tsx](../src/renderer/src/components/TopBar.tsx) 的“AI 执行计划”入口目前跳转自动化页面；[AutomationPage.tsx](../src/renderer/src/pages/AutomationPage.tsx) 是人工编辑流程，不能视为现有 Agent。
- [ApisPage.tsx](../src/renderer/src/pages/ApisPage.tsx) 及 [store.ts](../src/renderer/src/store.ts) 已管理项目、当前环境、活动接口、草稿和请求记录，可作为用户明确授权后提供给 Agent 的上下文来源。

发送给模型的上下文应是有边界的快照，而非直接暴露整个 Zustand store。明确区分活动编辑草稿与已保存版本，显示所选项目、接口及环境，并允许用户移除上下文。

### 3.2 现有工具与权限

[工具注册表](../src/main/mcp/tools.ts) 已定义 `upsert_api`、`list_apis`、`get_api_detail`、`execute_api`，以及流程、用例等工具，并提供工具列表、权限检查和调用入口。工具执行封装了目标变更跟踪。

`execute_api` 在 `save_response: true` 时还会写入响应文档；授权必须根据实际参数同时判断执行与写入，不能仅依赖工具声明的 `requires_write: false`。生成及更新接口文档须保留现有硬性文档校验；业务含义未知时应向用户澄清，不得猜测。

现有 `callTool` 的授权绑定 MCP 配置中的启用状态、允许项目、写入及执行开关，部分工具还会更新 MCP 配置。因此不应通过伪造启用配置直接调用来实现内置 Agent。

建议提取共享的 `ToolRegistry`、执行上下文和策略接口：业务实现复用，MCP adapter 与 Agent adapter 分别确定身份、项目范围、写入与执行权限；保留原有 MCP 行为及配置语义。

### 3.3 草稿、版本和变更通知

- [targetSync.ts](../src/shared/targetSync.ts) 的变更来源目前是 `mcp`、`ui`、`system`；Agent 应增加独立来源。
- [changes.ts](../src/main/storage/changes.ts) 负责目标变更广播；[renderer store](../src/renderer/src/store.ts) 接收同步时保护有未保存修改的草稿。
- [store.ts](../src/main/storage/store.ts) 的 `saveTargetChecked` 以已保存的磁盘定义计算 revision，能检测已保存定义的并发变化；未保存草稿的编辑不会改变该 revision。
- [apiDocumentation.ts](../src/main/mcp/apiDocumentation.ts) 的文档写入路径最终直接保存目标；不能假设现有所有 MCP 写入都具备 revision 检查。

建议新增双重校验：生成预览时记录已保存定义的 revision 和编辑草稿的快照或编辑版本；应用时分别检查相应状态。比较基线、当前草稿和提案，自动合并无冲突字段，仅对冲突字段请求确认；数组等细节仍需设计，不能静默覆盖。现有外部同步对 dirty 草稿的保护不代表 AI 应用已有草稿校验机制。变更来源及 operation ID 应贯穿工具执行和同步事件。

当前 UI 发送请求使用活动编辑草稿，MCP `execute_api` 则读取磁盘中已保存的定义。已确认助手默认修改草稿并用草稿测试；保存定义须作为独立计划步骤获批。具体执行快照及字段合并细节按规格在实施阶段验证。

### 3.4 取消能力

现有 `execute_api` 未贯穿 `AbortSignal`，而 [ipc.ts](../src/main/ipc.ts) 中界面请求路径已有取消控制。聊天取消需要传递到模型流和正在执行的工具，不能宣称现有 MCP 工具已普遍支持取消。

对暂不支持取消的工具，应停止后续步骤、明确显示当前操作可能仍在完成，并避免承诺已回滚。

## 4. 建议架构

```text
Renderer: AgentPanel + 上下文选择 + 流式消息 + 变更预览/确认
                 │ IPC（会话、事件、取消、审批）
Main: AgentRuntime / 会话协调 / 权限策略 / 审计
         ├─ Provider adapter → 用户配置的模型服务
         └─ 共享 ToolRegistry → 现有存储、请求执行器、流程能力
                                ↑
                         外部 MCP adapter
```

内置 Agent 在同一主进程中直接调用共享工具层，不需要经本机 TCP 或 stdio 绕回 MCP 服务。模型消息、工具调用、结果、审批和错误统一使用带 `sessionId`、`turnId`、`operationId` 的事件，确保多次交互互不串流。

### 4.1 运行时与模型

可评估 [AI SDK Core 工具调用](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling) 和 [Agent 概览](https://ai-sdk.dev/docs/agents/overview)：提供工具描述、输入 schema、执行函数、流式生成及多轮工具调用等能力。它只是 Kindra 的候选方案，不表示 Apipost 使用该 SDK，也不要求引入 Next.js。

实现前验证所选版本对 Electron 主进程、目标模型接口、流式工具调用及取消的支持；通过 provider adapter 隔离 SDK，避免 UI 和业务工具绑定某个厂商。先不锁定具体 SDK 版本。

模型设置应支持多个本机连接配置及项目默认值，每轮任务固定配置、不自动切换服务；允许用户填写 API 地址、Key 和模型名；首批支持 OpenAI 兼容接口，明确配置 Chat Completions 或 Responses 并测试能力；仅支持文本的模型不启用工具连续操作。具体兼容范围待定，自填地址不意味着支持任意 API 协议。连接测试只发送最小测试消息，不记录 Key，并提供清晰的连接错误提示。

### 4.2 上下文与脱敏

默认在当前项目内脱敏读取完成任务所需内容，并展示将发送的内容；允许读取和操作未保存草稿，保存定义需单独授权；执行快照细节在实施阶段验证。请求头、Cookie、认证信息、环境变量、响应中的敏感字段默认遮蔽或排除，并对大响应做截断。

用户明确选择提供额外内容时，界面应说明内容会发送到所配置的模型服务。工具返回值同样执行脱敏及大小限制，避免通过工具结果绕过上下文控制。

### 4.3 凭据和会话

模型 Key 由主进程保存和用于模型请求，使用 Electron [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) 异步接口加密，并检查当前平台加密可用性。设置界面输入的 Key 通过专用 IPC 提交，保存后清除输入；普通配置读取仅返回是否已设置，不回传明文 Key，也不将其写入项目或 Git。加密不可用时明确告知用户并采用经用户选择的处理方式。

建议模型配置放在本机 `offline-data-local/settings`，项目会话放在 `offline-data-local/projects/<projectId>/agent/`，沿用 [storage/store.ts](../src/main/storage/store.ts) 的本地数据布局。会话按项目在本地保存，支持删除和重启续聊，不进入 Git；保存需应用同样的脱敏规则，保留至用户手动删除。

### 4.4 工具及审批

按已确认的接口、单接口用例、执行分析和跨接口流程能力分组注册最小必要工具；具体清单按现有工具拆分结果确定。

| 操作类型 | 默认策略 | 用户体验 |
| --- | --- | --- |
| 读取 | 限定当前项目和已授权范围，结果脱敏 | 展示读取对象和结果摘要 |
| 写入 | 先形成结构化变更，确认后分别校验保存定义 revision 和草稿快照或编辑版本 | 展示字段级差异、目标和冲突 |
| 执行 | 按本轮计划明确授予对象、环境和操作范围；主进程逐步校验 | 展示执行中、结果及失败原因；高风险或超范围时再次确认 |
| 高风险能力 | 首期不开放 shell、任意 SQL、任意文件写入 | 不向模型注册相关工具 |

权限在主进程执行时再次检查，不能仅依赖模型提示或 Renderer 的按钮状态。限制工具轮次、执行时间、返回字节数和重复调用次数；对错误返回可理解的原因，避免无限重试。

## 5. 首版范围与建议交互

首版已确定支持连续操作 Agent；首版覆盖 HTTP 接口、单接口用例、请求及用例执行分析和跨接口执行流程。以下是交互建议；具体工具、执行快照及字段合并细节尚待确定。

1. 用户打开右侧面板，选择当前接口或请求结果，看到上下文与脱敏提示。
2. 用户要求解释接口或分析错误，助手流式回复并显示必要的只读工具活动。
3. 用户要求生成接口或测试用例，助手生成结构化草案，面板展示目标、字段差异和依据。
4. 用户确认后，再次检查项目权限、保存定义 revision 和草稿快照或编辑版本，将无冲突的变更应用到草稿，对冲突字段请求确认；保存定义须是独立获批步骤。
5. 用户要求执行测试时，展示方法、URL、环境和可能影响；在已批准的本轮计划范围内逐步校验并执行，范围扩大或发生冲突时再次确认。
6. 用户可以取消生成；界面反映实际取消状态，不把无法中断的操作显示为已撤销。

首版具体工具集合待确定；字典、MQTT 等未纳入已确认范围。

## 6. 实施顺序

1. 细化首版工具清单、计划授权、草稿保存与执行快照，并验证两种已选协议的模型能力。
2. 提取共享工具注册、执行上下文与独立策略，保留外部 MCP 现有行为并补充回归覆盖。
3. 实现 Agent loop、当前项目脱敏上下文、模型配置、安全存储、流式交互和可取消执行。
4. 实现项目会话保存、删除和重启续聊，并按已确定的草稿策略提供变更预览和双重校验。

建议模块（以下均为尚未创建的示意路径，实施时按现有目录调整）：

- `src/renderer/src/components/AgentPanel.tsx`：入口、上下文与进度。
- `src/renderer/src/components/AgentPreview.tsx`：结构化差异和应用确认。
- `src/main/agent/runtime.ts`：任务协调、流事件及取消。
- `src/main/agent/provider.ts`：模型适配与配置。
- `src/main/agent/schemas.ts`：任务专用输入与生成结果 schema。
- `src/main/agent/policy.ts`：执行范围与权限检查。
- `src/main/tools/registry.ts`：共享工具注册和适配。

每一步独立验证，避免在重构权限和引入模型时同时改变外部 MCP 的行为。

## 7. 验收场景

- 使用选中的示例接口提问，回答与选择的接口一致；切换项目后旧会话不会读取新项目之外的数据。
- 包含认证头和环境密钥的请求进入上下文时，模型侧只收到脱敏值；日志与会话文件不出现明文 Key。
- 助手提出接口修改时，在确认前磁盘数据不变；拒绝后无写入；确认后只改变预览范围。
- 预览后比较基线、当前草稿与提案；无冲突字段自动合并，冲突字段请求确认，不静默覆盖。保存时另检查已保存定义 revision。
- 执行请求前展示目标及环境；拒绝后不发送请求；允许后记录可见结果和错误。
- 生成过程中取消可中止模型流；支持取消的工具收到取消信号，不支持的工具如实显示状态。
- 禁用外部 MCP 或收紧其权限不应绕过或意外改变内置 Agent 的独立策略，反之亦然。
- 切换项目后任务继续绑定原项目和获批环境；退出前提示运行中的任务，重启不自动重放网络请求。
- 批量执行保留已成功对象，失败对象及其依赖暂停，独立步骤继续；重试只针对未完成步骤，远端结果未知时不自动重发。
- 断网、模型错误、流中断、超时和重复提交均能结束加载状态，且不会重复写入。

### 执行与恢复的现有边界

- [executor.ts](../src/main/request/executor.ts) 的请求执行包含前后脚本及运行后变量写回；执行授权需要考虑这些副作用。
- 现有取消能力未贯穿 MCP、用例和 Flow 的执行链；停止不能假定会撤销已经发生的操作。
- [store.ts](../src/main/storage/store.ts) 的版本恢复不覆盖用例，不能当作完整 Agent 撤销；多接口操作也没有整批原子事务，可能部分成功。
- Agent 执行应显式绑定 `environment_id`，避免执行中 UI 全局环境改变导致目标漂移。既有脚本、变量更新、额外请求和已配置文件上传按实际行为纳入计划授权；新增或修改脚本、扩大目标或文件范围时重新核对授权。整轮本地撤销须检查冲突并使用 Git Diff 风格界面；远端请求不回滚。未知业务字段的交互仍待产品决策。

### Flow 草稿与执行快照

[AutomationPage.tsx](../src/renderer/src/pages/AutomationPage.tsx) 的 Flow 草稿目前保存在页面状态，执行前先保存；[IPC](../src/main/ipc.ts) 再从磁盘读取。Flow 的 API 节点逐次从存储读取接口，`sendRequest` 还实时读取继承参数、模型、变量和 Cookie。因此，执行未保存草稿需要新增快照读取边界；可考虑冻结定义、保留运行时可变变量和正常登录 token 数据流，而不是冻结所有运行数据。

Flow 入口与 API 节点对传入环境的覆盖处理目前不一致，需要实现时修复并验证。接口前后脚本可通过 `pm.sendRequest` 发出额外网络请求；主请求的 binary/form-data 文件上传通过文件解析器读取已配置文件。独立 Flow 脚本没有显式注入网络或文件系统能力；使用 `node:vm` 本身不构成强安全隔离的保证。

现有 Flow 运行报告位于项目 Git 目录；Agent 会话不进入 Git 不意味着这些报告自动排除，既有手动 Flow 报告不迁移；Agent 对话、计划、工具结果和报告本地保存、不进 Git，保留至手动删除。

### 草稿生命周期与合并的技术约束

当前 [App.tsx](../src/renderer/src/App.tsx) 的退出保护会自动保存 dirty API，与 Agent 保存须独立授权的规则冲突；主进程窗口关闭按钮目前隐藏到托盘，真正退出走 `requestQuit`。切换项目时现有接口 store 清除草稿，而 Flow 草稿位于页面局部状态。跨项目持续任务需要独立于页面路由、按项目和实体标识管理草稿的能力；退出时仅暂存 Agent 改过的草稿，重启可恢复，不正式保存定义；纯手动草稿沿用现状。

三方合并建议按 `param_id`、`case_id`、`event_id` 等稳定 ID 识别实体；字段指针只是路径，不能仅凭名称或路径认定重命名前后是同一实体。raw body 和脚本字符串建议作为整体进行三方比较，不让模型暗中改写后合并；具体规则仍需设计。

Agent 执行尝试需要单独表示远端结果未知，现有发送记录不能充分表达此状态。计划应显式记录步骤依赖；不能证明独立的步骤按依赖关系暂停，独立步骤继续不要求引入并行执行。

### 候选版本的现有实现边界

[存储实现](../src/main/storage/store.ts) 的正式接口版本已位于本机版本目录；正式接口定义才位于 Git 项目目录。现有保存定义时才记录正式版本，未标记版本最多保留 100 条，带 Tag 的版本不裁剪。不能调用 `saveTarget` 来制造候选，否则会隐式正式保存。版本抽屉目前只提供历史、Tag 与恢复，没有候选状态或快照 diff；现有恢复不覆盖用例和自定义属性，不能充当完整 Agent 撤销。

建议候选使用独立本机集合，与正式版本在 UI 合并查询，不插入现有版本数组；候选使用独立编号，未解决候选不受 100 条裁剪。现有版本签名与定义 revision 对可编辑字段的口径不一致，需统一语义，同时保持各自标识。删除或尚未正式创建的对象需要项目级候选汇总及独立墓碑，保留审阅和撤销证据；Flow 需新增同等版本能力。不采纳只改变审阅状态并保留历史，已应用草稿的撤销需另行检查冲突。现有 Git Diff 针对 Git 文件，候选需新增快照 diff 并复用视觉风格。
