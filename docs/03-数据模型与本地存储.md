
### 1.1 两种作用域

| 作用域 | API | 根目录 | 用途 |
|---|---|---|---|
| project | `projectRead/projectWrite/...` | `<项目目录>` | 接口、环境、全局参数等，可被 git 管理 |
| local | `localRead/localWrite/...` | `offline-data-local` | 发送历史、最近打开、个人配置等 |

`project_storage.json` 可覆盖默认项目根目录（`last_storage_path`）。

## 2. 通用仓储模式

`152012` 模块提供通用 CRUD：

- 索引：`<dir>/index.json` = `{ project_id, items: [...] }`
- 实体：`<dir>/<id>.json`
- `list()`：读取 index；`getAll()`：先 list 再逐个读实体
- 仓储定义：

| dir | 主键 | 作用域 |
|---|---|---|
| `apis` | `target_id` | project |
| `samples` | `sample_id` | project |
| `schemas` | `model_id` | project |
| `envs` | `env_id` | project |
| `history` | `history_id` | local |

`findProjectEntity(dir, id)` 可直接按 id 找实体。

### 2.1 写入语义（fileDB）

以下为【事实】——通过动态加载 `utils/fileDB.jsc` 读取导出与原型方法确认：

- 导出：`FileDB`、`fileDBInit`、`getFileDB`。
- 原型方法：`readJson / writeJsonAbs / deleteJsonAbs / listDirJson / atomicWrite /
  persistOne / flush / getRegistry / saveRegistry / getRoot / getProjectPath /
  resolveProject / resolveLocal / ensureProjectDir / isInsideManagedData /
  stringifyStable / sortKeysDeep / notifyMockIndex / selfTest / log`。
- **原子写**：`atomicWrite` + `writeJsonAbs`（临时文件 + rename）。
- **防抖合并**：`pendingData` + `timers` + `persistOne/flush`；`before-quit`
  两段式 flush，3 秒超时保护（`main.js`）。
- **损坏恢复**：`store.jsc` 有 `backupCorrupt`；`fileDB` 的原型上没有
  同名方法，其坏 JSON 处理细节与 `.broken.<timestamp>` 命名**未能确认**。
- **锁**：`preload.js:86-87` 确实暴露了
  `acquireLock(name)` / `releaseLock(name)`（IPC）；但 `fileDB.jsc`
  的原型上没有同名方法，锁的具体实现位于主进程 handler，**未逐行确认**。
  MCP 侧另有 `project:flow` 运行锁（见 08）。
- **索引缓存失效**：写/删 `apis`、`settings` 会调用 `notifyMockIndex`
  （动态探针确认该方法存在）。

### 3.4 request 对象

```json
{
  "auth": { "type": "inherit" },
  "header": { "parameter": [] },
  "query":  { "parameter": [], "query_add_equal": 1 },
  "restful":{ "parameter": [] },
  "cookie": { "parameter": [], "cookie_encode": 1 },
  "body": {
    "mode": "none",               // none | raw | json | xml | javascript | plain | html | urlencoded | form-data | binary | msgpack
    "parameter": [],
    "raw": "",                    // 原始文本（mode=raw 时使用）
    "raw_parameter": [],
    "raw_schema": { "type": "object" },
```

> 【事实】body 的模式值是 `form-data`（带连字符），不是 `formdata`；
> `raw` 是字段而不是模式。发送引擎内部会把它再映射成 postman 的
> `formdata`（`analysis/pretty/842216.js:1690`）。文件型表单字段通过
> `field_type === "file"` 判定（同文件 `:1703-1704`），不是 `type`。

参数项（header/query/restful/cookie/body.parameter）：

```json
{
  "param_id": "1f...",
  "key": "Content-Type",
  "value": "application/json",
  "description": "",
  "field_type": "string",
  "is_checked": 1,
  "is_system": -1,
  "schema": {},                  // 可选的 JSON Schema（用于自动生成值）
  "not_null": -1
```

`is_checked > 0` 才会被发送；`is_system > 0` 为系统头（自动加）。
`query.query_add_equal` 默认 `1`，`cookie.cookie_encode` 默认 `1`；
`restful`/`cookie` 的 `parameter` 与 header 同构。

### 3.6 目录继承与合并规则（很重要）

请求会沿目录链向上合并：

1. 从当前接口向上找 `parent_id`，直到 `"0"`（项目根）。
2. 根使用 `global_params.json`，中间目录和接口使用各自的 `request`。
3. `header/query/cookie/body.parameter` 按 `key` 合并：
   - 子级优先；
   - header 的 key 不区分大小写；
   - 只合并 `is_checked > 0` / `is_system > 0` 的项。
4. `auth` 为 `inherit` 时继承父级；否则使用自身。
5. `pre_script/test/post_tasks/pre_tasks` 向上拼接（父级在前）。
6. `server_id`：子级显式设置优先，否则继承父级；最终用于环境 `server_list` 的前缀 URL。

### 3.7 环境（envs/<env_id>.json）

```json
{
  "env_id": "1",
  "project_id": "2da28c0efcd003",
  "name": "默认环境",
  "env_var_list": {
    "baseUrl": { "key": "baseUrl", "value": "https://api.example.com", "current_value": "https://api.example.com", "description": "", "static": true }
  },
  "server_list": [
    { "server_id": "1", "name": "default", "uri": "", "sort": 1000 }
  ],
  "is_private": -1,
  "sort": 1000,
  "created_at": "...",
  "updated_at": "..."
}
```

`envs/index.json` 只存 `{env_id,name,sort,updated_at}` 列表。

- 【事实】环境变量行的默认结构是
  `{key, value, current_value, description, static: true}`；保存时按 `key`
  映射整行。旧版写的 `initial_value / is_checked` 是错的。
- `server_list[].uri` 会作为请求前缀（`pre_url`）；发送时按 `server_id`
  在 `env_pre_urls` 的值中查找，而不是用 `env_pre_urls[server_id]` 直接下标
  （`analysis/pretty/842216.js:1305`）。
- 环境变量最终进入 postman runtime 的 `environment` 作用域。

### 3.8 全局变量与全局参数

- `global_params.json`：项目级请求默认值（结构同 `request`）。
- 全局变量（global vars）：`global_vars.json` 属 project 作用域；
  `global_vars_history.json` 位于 local 作用域
  （`offline-data-local/projects/<pid>/`）。
- 系统配置（本机）：`offline-data-local/settings/user_configure.json`，关键字段：

| 字段 | 含义 |
|---|---|
| `send_timeout` | 请求超时（秒）。发送前会钳制到 `[0, 604800]`，非法值置 0（`analysis/pretty/842216.js:1881-1882`） |
| `auto_redirect` | 自动跟随重定向（>0） |
| `max_redirect_time` | 最大重定向次数（最小 5） |
| `follow_original_method` | 重定向后保持原方法 |
| `request_param_auto_json` | 参数自动 JSON 化 |
| `proxy` / `request_proxy_*` | 代理配置 |
| `ca_certificate` / `client_certificate` | TLS 证书 |
| `global_cookie_open` | 全局 Cookie 开关 |
| `auto_gen_mock_url` | 自动生成 Mock URL |

### 3.9 状态标记（settings/marks.json）

```json
[
  { "mark_id": "1", "project_id": "...", "name": "开发中", "color": "#2857FF", "is_default_mark": 1, "is_sys_default": 1 },
  { "mark_id": "2", "name": "已完成", "color": "#26CEA4", "is_default_mark": -1, "is_sys_default": 1 }
]
```

【事实】接口状态枚举来自渲染层模块：
`DEVELOPING="1" | COMPLATED="2" | MODIFYING="3" | ALL="all"`，
默认标记 `mark_id` 为 1–4（开发中/已完成/需修改/已废弃），
不存在旧版所列的 `designing/testing/released/obsolete` 等字符串枚举。


> 注意：`result_id` 实际等于对应的 `history_id`。`response` 里的 body
> 以文本保存；二进制/大文件需另存。

### 4.4 版本历史（history/，local）

- 目录：`offline-data-local/projects/<pid>/history/`
- 索引项：`{history_id, target_id, version, created_at, tag}`；
  【事实】索引里的 `tag` 恒为 `""`。
- 实体：`{history_id, project_id, target_id, version, tag, details, created_at, updated_at}`。
  【事实】写入前会对 `details` 做 `JSON.parse`，落盘是**对象**，不是字符串
  （旧版写反了）。
- 每次保存接口时生成一个版本；每个 `target_id` 最多保留 100 个版本。

## 5. 数据模型（schemas）与示例（samples）

### 5.1 数据模型

```json
{
  "model_id": "...",
  "project_id": "...",
  "parent_id": "0",
  "model_type": "model",          // model | folder
  "name": "User",
  "sort": 0,
  "version": 1,
  "status": 1,
  "data": {
    "description": "",
    "schema": { "type": "object", "properties": { ... } }
  },
  "created_time": "...",
  "updated_time": "..."
}
```

【事实】`schema` 与 `description` 在 `data` 内，不在顶层；时间字段是
`created_time / updated_time`。列表接口会把 `data.schema` 扁平化后返回，
不要据此反推落盘结构。`schema` 是 JSON Schema 的扩展（含
`x-schema-orders` 等展示信息）。

### 5.2 示例（sample）

接口的样例数据。元信息在顶层
`sample_id / parent_id / target_id / type / name / url / method / sort`，
内容在 `data` 内（部分旧数据用 `details` 存 JSON 字符串）。`samples/index.json`
在源码中**未观察到写入**，列表以目录扫描为主；请把它视为可选缓存。
在测试用例里作为 `type: "sample"` 事件使用。

## 8. ID 规则

观察到的 ID 形如：

- `2da28c0efcd003`（项目）
- `2dd0d49dfcd002`（目录）
- `1f97b28f17ffffe`（Mock 规则）
- `1f97b28f1800000`

特征：十六进制字符串；观察到的长度是 14~15 位（项目/目录 14 位，
规则 ID 15 位），旧版写的 15~17 偏大。末几位呈递增趋势（类似雪花 ID + 前缀）。
**复刻时把它当作不透明字符串即可**，只需保证：

- 全局唯一；
- 可按字典序/时间粗略排序（可选）；
- 不要用自增整数（多项目合并时容易冲突）。

## 9. 复刻时可简化的点

1. 不需要实现 `.jsc` 字节码；直接明文模块即可。
2. 不需要实现多副本 / 系统锚点 / 时钟回拨（那是授权，不是业务）。
3. 索引文件可以保留，也可以直接用文件系统扫描；保留的好处是列表加载快、易于排序。
4. 版本历史可以先不做；发送历史建议保留（你的核心需求是「记录调用响应」）。
5. 版本历史的 `details` 在原应用中先序列化、写入前再解析为对象；新实现直接存对象即可。
