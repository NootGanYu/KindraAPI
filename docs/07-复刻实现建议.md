# 07 · 复刻实现建议

> 目标：做一个自己的「接口调用 + 响应记录 + 简单流程自动化」工具。
> 不依赖、也不绕过原软件的授权。

---

## 1. 先明确产品边界

### 1.1 你的 MVP 必须有的

1. **接口管理**：目录树、接口增删改查、环境变量。
2. **请求调试**：HTTP（含 JSON / form / 文件）、Header/Query/Cookie/Auth。
3. **响应展示**：状态码、耗时、大小、Header、Body、Timings。
4. **调用记录**：每次发送保存 request/response，可回放、可比较。
5. **简单自动化**：顺序步骤 + 变量提取 + 断言 + 等待 + 条件/循环（可后置）。

### 1.2 可以后置的

- WebSocket / Socket.IO / gRPC / TCP / 数据库
- Mock 服务与文档分享
- 压测 / 并发执行 / 定时任务
- 版本历史 / git 协同 / MCP / 热更新
- AI 生成用例

## 2. 技术选型建议

### 2.1 桌面壳

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Electron** | 与参考实现同构；Node 生态直接可用；`postman-runtime` 可直接跑 | 包体大、内存高 |
| Tauri | 包体小、内存低 | 请求运行时需要用 Rust/Node sidecar；脚本沙箱更麻烦 |
| 纯 Web + 本地服务 | 开发简单 | 跨域、文件访问、证书、代理更麻烦 |

**建议**：如果优先「快速复刻 + 最大兼容」，选 **Electron**。

### 2.2 请求执行

**强烈建议直接使用 `postman-runtime` + `postman-collection`**：

```bash
npm i postman-runtime postman-collection
```

理由：

- 已经解决了重定向、代理、TLS、HTTP/2、Cookie、multipart、脚本、断言、变量作用域。
- 你只需要写「自有模型 → Postman 模型」的转换层。
- 将来要兼容 Postman 脚本，几乎零成本。

如果不想依赖 Postman 生态，可以用 `undici` / `got` 自己实现，但要准备处理大量边界情况。

### 2.3 存储

| 方案 | 适用 |
|---|---|
| **JSON 文件 + 目录** | 与参考实现一致，适合 git 协同、离线、易调试 |
| SQLite | 单文件、查询强，但不利于 git diff |
| IndexedDB | 纯前端，难跨设备/难备份 |

**建议**：保留「一项目一目录 + JSON」；用 SQLite 做「历史/日志」的二级存储也可以。

### 2.4 UI

- React + Ant Design（与参考实现一致，组件齐全）
- 状态：Zustand（轻量）
- 编辑器：Monaco（JSON/脚本）
- 请求列表/树：虚拟滚动（大项目必备）

### 4.5 流程

```ts

  flow_id: string;
  project_id: string;
  name: string;
  steps: Step[];
  settings: {
    env_id: string;
    execute_count: number;
    interval_time: number;
    ignore_error: boolean;
  };
}
```

### 4.6 简化模型 ↔ 实测字段映射

本节是**建议模型**，不是原应用的落盘契约。对接/导入时必须按右列转换：

| 本文（建议） | 原应用实测 | 说明 |
|---|---|---|
| `SendRecord.history_id` | `history_id`（索引）/ `result_id`（结果文件，实际等于 `history_id`） | 见 03 §4.2/§4.3 |
| `SendRecord.created_at` | `updated_time` / `created_at` | 见 03 §4.2 |
| `Flow.flow_id` | `testing_id`（测试用例）或 `flow_id`（MCP 执行流程） | **两个概念，别混** |
| `Step` | `event`（`event_id/type/enabled/data/children`） | 见 03 §6、05 §3 |
| `Step.type="http"` | `event.type` 为 `api/sample/request/sse` | 没有统一的 `http` 类型 |
| `Step.type="assert"` | `event.type` 为 `assert` 或 `assert_visual`（后者数据在 `data.data`） | 见 05 §3.3/§3.4 |
| `Flow.settings` | `settings` + 同级 `frequency` | `frequency` 不在 settings 内 |
| `Flow.settings.ignore_error: boolean` | `ignore_error: 1 \| 0`（默认 1） | 数值开关 |
| `BodyModel.formdata`（字段名） | `mode="form-data"`（模式值） | 字段名是 `formdata`，mode 值是 `form-data` |

> **术语警告**：原应用里有两种“流程”——
> 1. **测试用例/事件树**（`testing`，本地 CRUD 未落地，见 03 §6/05）；
> 2. **MCP 执行流程**（`executions/flows`，由 AI 创建，见 08）。
> 本文的 `Flow` 若指后者，字段应直接采用 08 的 `flow_id/steps[].step_id`；
> 若指前者，应改用 `testing_id/event_list`。

## 5. 请求执行层设计

### 5.1 转换层

```ts
function toPostmanItem(target: Target, resolved: ResolvedRequest): Item {
  // 1. URL
  const url = buildUrl(resolved);
  // 2. header/query/cookie
  const header = resolved.header.parameter.filter(p => p.is_checked > 0);
  // 3. body
  const body = toPostmanBody(resolved.body);
  // 4. auth
  const auth = toPostmanAuth(resolved.auth);
  // 5. scripts
  const events = [
    resolved.pre_script && { listen: "prerequest", script: { exec: [resolved.pre_script] } },
    resolved.test && { listen: "test", script: { exec: [resolved.test] } },
  ].filter(Boolean);

  return new Item({ name: target.name, request: { url, method, header, body, auth }, event: events });
}
```

### 5.2 执行

```ts
async function execute(item: Item, ctx: RunContext): Promise<StepResult> {
  const collection = new Collection({ info: { name: ctx.name }, item: [item] });
  return new Promise((resolve, reject) => {
    new Runner().run(collection, {
      requester: {
        strictSSL: ctx.tls.strict,
        followRedirects: ctx.http.followRedirects,
        maxRedirects: ctx.http.maxRedirects,
        protocolVersion: ctx.http.protocol,
      },
      systemProxy: ctx.http.proxy,   // postman-runtime 读顶层
      timeout: { request: ctx.http.timeout, script: 0, global: 0 },
      environment: new VariableScope({ values: toValues(ctx.env) }),
      globals: new VariableScope({ values: toValues(ctx.globals) }),
      localVariables: new VariableScope({ values: toValues(ctx.vars) }),
      data: ctx.iterationData,
    }, (err, summary) => {
      if (err) return reject(err);
      summary.start({
        response: (err, response, request, ...) => {
          if (err) reject(err);
          else resolve(snapshot(response, request));
        },
        assertion: (assertions) => { ctx.assertions.push(...assertions); },
        console: (level, ...args) => { ctx.console.push({ level, args }); },
      });
    });
  });
}
```

### 5.3 响应快照

至少保留：

- `request`: url / method / headers / body
- `response`: code / status / headers / body / mime / size
- `timing`: 总耗时 + 分阶段
- `assertions`
- `console`
- `error`

> 大响应：body 超过阈值（如 256KB）落文件，记录中只存文件路径 + hash。

## 6. 流程自动化设计

### 6.1 执行器

```ts
async function runFlow(flow: Flow, ctx: RunContext) {
  ctx.emit({ type: "flow-start", flow_id: flow.flow_id });
  for (const step of flow.steps) {
    if (ctx.aborted) break;
    ctx.emit({ type: "step-start", step_id: step.id });
    try {
      await runStep(step, ctx);
      ctx.emit({ type: "step-end", step_id: step.id, ok: true });
    } catch (e) {
      ctx.emit({ type: "step-end", step_id: step.id, ok: false, error: String(e) });
      if (!flow.settings.ignore_error) break;
    }
  }
  ctx.emit({ type: "flow-end", summary: summarize(ctx) });
}
```

### 6.2 变量

- 三层：`env` / `globals` / `run`。
- 替换 `{{name}}` 时按 `run > env > globals`。
- 脚本可写 `run`；是否允许写 `env` 由产品决定。

### 6.3 断言

建议先支持：

- 主体：响应 JSON / 文本 / Header / 状态码 / 耗时
- 操作：等于、不等于、大于、小于、包含、存在、正则、为空
- 路径：JSONPath

### 6.4 取消

- 每个 HTTP 步骤支持 `AbortController`。
- 流程级取消立即停止后续步骤。
- 如果放在 Worker，直接 `worker.terminate()`。

## 7. 里程碑

### M1（1~2 周）——可用的请求调试器

- 项目/目录/接口 CRUD
- 环境变量
- HTTP 请求 + 响应展示
- 发送记录（request/response 落盘）

验收：能把一个真实接口跑通，并在历史里看到完整请求与响应。

### M2（1~2 周）——记录与回放增强

- 历史列表、搜索、详情对比
- 响应体大文件落盘
- 导出 HAR / cURL
- 失败请求也完整记录

验收：能对比两次调用差异，定位接口变化。

### M3（2~3 周）——简单流程自动化

- 顺序步骤（HTTP / script / assert / wait）
- 变量提取与替换
- 单条件 if
- 按数组循环
- 执行日志 + 汇总报告

验收：能跑「登录 → 取 token → 查询 → 断言」的完整链路。

### M4（可选）——Mock / 压测 / 分享

- 固定响应 Mock
- 顺序/并发执行
- 文档导出

## 8. 测试策略

1. **模型转换单测**：给定 Apipost 模型，断言生成的 Postman Item 正确。
2. **Golden HAR**：真实接口跑一次，保存 HAR；后续对比关键字段。
3. **变量优先级测试**：env / globals / run 同名覆盖。
4. **边界测试**：空值参数、重复 header、UTF-8、二进制、重定向、超时、证书错误。
5. **流程测试**：断言失败是否中断、循环是否隔离变量、取消是否及时。
6. **存储测试**：并发写、崩溃恢复、大文件、路径穿越。

## 9. 常见坑清单

| 坑 | 建议 |
|---|---|
| `{{var}}` 替换时机不对 | 统一在「发送前」替换；脚本改动后重新替换 |
| header 大小写 | 合并时忽略大小写，发送时保留原样 |
| 空值 query | 明确 `key=` 还是省略；用配置控制 |
| 重定向改方法 | 提供 `followOriginalHttpMethod` 开关 |
| TLS 证书 | 默认严格校验；提供「忽略证书」显式开关 |
| 大响应 | 落文件 + 截断预览；不要塞进 JSON 历史 |
| 并发写文件 | 单写队列 + 原子 rename |
| 时间显示 | 统一 UTC 存储、本地时区展示 |
| 撤销/版本 | 先做自动保存版本，别一开始做实时协同 |
| 授权 | 自己产品的授权请自行设计，不要复用/绕过他人授权 |

## 11. 最小可行代码骨架

```ts
// storage.ts
export async function readJson<T>(file: string, fallback: T): Promise<T> {
  try { return JSON.parse(await fs.readFile(file, "utf8")); }
  catch { return fallback; }
}

export async function writeJsonAtomic(file: string, data: unknown) {
  const tmp = `${file}.${process.pid}.tmp`;
  await fs.mkdir(path.dirname(file), { recursive: true });
  await fs.writeFile(tmp, JSON.stringify(data, null, 2));
  await fs.rename(tmp, file);
}

// request.ts
export async function sendRequest(req: RequestModel, env: EnvContext) {
  const resolved = resolveVariables(req, env);
  const item = toPostmanItem(resolved);
  return execute(item, env);
}
```

## 12. 结论

复刻这套工具的关键不是「写一个 HTTP 客户端」，而是三件事：

1. **稳定的数据模型**（接口/环境/记录/流程）
2. **正确的请求转换与变量解析**
3. **可回放的响应记录**

把这三件事做好，再逐步加 Mock、流程、压测，就是一个可用且可持续演进的产品。
